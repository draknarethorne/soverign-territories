# Recap: 2026-10-24, crop sequence, framing and named folders

Follow-up to the [visual UAT recap](2026-10-23-2121-recap.md). This is a
sandbox checkpoint: no commit, push, live move or GPU job.

## The day in a few lines

The user asked four things:

- whether recommendations were really verified;
- for crop → erase → crop, with a final crop that centres the person and trims
  background;
- for simple, composable flows, with Various as the single drop point;
- for retained version sets that follow the identity, and recovery of the
  `Various\<Name>\gallery` drop.

The [intake plan](../../plans/2026-10-23-image-intake-preparation.md) holds the
verbatim messages, the honest answer, the visual tables and tasks I21–I26.

Honest answer: no. Before v14 no second crop was ever selected, so the
recommendation was at best the first panel crop. There was also no final
framing crop: it existed only after assignment, in `likeness crop`.

What we delivered:

- **v14** selects a pure overlay crop under guards: ≥95% of the mask removed,
  ≤25% area lost, a body frame around every face, and either screenshot
  evidence or one compact corner logo. Both GMW-logo samples are now clean.
- **v15** adds a `composition` step. It reuses the gallery's `person_box`, so
  intake and the gallery frame the same way. Order: crop → eraser trial →
  overlay crop → framing → enhancement comparisons.
- **`likeness seed`** (step 0 of `library.cmd`) moves `Various\<Name>\gallery`
  to that person, existing or new. The regression came from the folder scan
  treating Various as a single pool.

## What was good

- Inspecting the images again exposed the gap between "a second crop is
  rendered" and "a second crop is chosen".
- Framing reuses the existing person crop instead of a new rule, so v15 can
  match production behaviour now and become redundant at the I12 cutover.
- Seeding is a separate, previewable step. It does not add a special case to
  sorting.

## What was bad

- Earlier summaries implied better recommendations than the code made. The
  user had to ask. Say "rendered, not selected" plainly next time.
- `...7310` loses shins and feet in its selected crop. The body-frame guard
  measures from the face, not from the visible body.
- Portrait-style screenshots are not framed at all, because the face is already
  wide. That is correct for portraits, but nothing trims side background there.

## What could be improved

- Intake I25: calibrate second-crop misses (mask specks in `123511`, 26% loss on
  the facebook capture, `...4360` refused, `...7310` feet).
- Intake I22: an intake-only stop/resume flag; I23: an all-versions page.
- Intake I21/I24/I26: user decisions (below).

## Recurring themes

Evidence before claims. Each step must be runnable alone and in the combined
routine. Archiving rules (`*_org`) and the proposed `gallery_org` retention
must not collide.

## Complexity and debt

`preparation_geometry.py` keeps growing guard heuristics. A small table of
named rules with their thresholds would be easier to audit. The recipe tuples
in `image_preparation.py` repeat every version; a single registry would remove
that repetition.

## Numbers

- Tests: 67 preparation, 58 likeness, 12 library routine. Full quick check:
  27 suites, 672 tests, 19/19 mutations. One provenance fixture relabelled a
  v15 manifest as v6. It now drops the composition step, as a real v6 manifest
  would.
- v14c: 262 files, 204.8 MB; v15: 265 files, 204.9 MB (12 sample inputs). The
  v14 and v14b scratch runs were deleted. Both remaining runs pass `--check`.
- A retained full PNG version set would be about 16.5 MB per photo, about
  6.6 GB per 400 photos. I21 proposes keeping only the manifest, the masks and
  the selected images.
