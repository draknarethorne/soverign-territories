# Daily recaps

One reflection per working day, written at the end of it, before the commit and push. It is where we look back at how the day went, so that the next day starts wiser.
The plans say what is open ([../todo.md](../todo.md) is the queue); the recap says what we learned.

## The file

`docs/recap/YYYY-MM-DD-HHMM-recap.md`, the date and the time it was written, so the files sort in order. A day that runs long and is reflected twice gets two files.

## What it contains

| Section | What goes in it |
| --- | --- |
| The day in a few lines | What we set out to do, what got done, what is still open (a link to the plans, not a copy) |
| What was good | Practices and decisions worth repeating, with the evidence |
| What was bad | What went wrong or cost time, honestly, and why |
| What could be improved | Concrete changes to the tools, the docs or the way we work; each one that is worth doing becomes a tagged box in a plan |
| Recurring themes | Things that keep coming back; look at the earlier recaps before writing this one |
| Complexity and debt | Code or documents that grew heavy, and what would simplify them |
| Numbers | A few that show the size of the day (files, tests, photos moved) |
| Top 3 for you | The three things you should do next, in order, with where to find them |

## How it is made

1. Re-read the day: the plans touched, `git log` and `git diff --stat`, the notes in `tmp/`, what the tools reported.
2. Write it plainly: what helped and what did not, including the assistant's own mistakes. No cheerleading.
3. Turn every "could be improved" that deserves work into a tagged box in a plan (`docs/plans/`), so it reaches [../todo.md](../todo.md).
4. Keep the top 3 short and actionable; they come from the queue, not from new ideas.

The recap is part of the day's hygiene in [../plans/README.md](../plans/README.md).
