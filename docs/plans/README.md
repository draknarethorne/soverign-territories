# Plans of action

One file per piece of work we agreed to act on. This is how we work day to day, so the other documents stay clean.

## The pattern

| Kind of document | Where | Rule |
| --- | --- | --- |
| Scratch thinking | `tmp/<topic>.md` (git-ignored) | Brain-dumps and drafts, free-form. Nothing depends on them. Keep the raw thoughts word for word when a draft is promoted |
| A plan we agreed to act on | `docs/plans/YYYY-MM-DD-<slug>.md` (this folder, tracked) | Starts as a tmp draft; becomes a plan when we agree to act on it |
| Current state | [../STATUS.md](../STATUS.md) | Decisions and open questions only. One line per active plan under "Active plans", no step-by-step detail |
| Your checklist | `docs/todo.md` | Generated by `bin\todo.cmd` from the finals and candidates kept in the repo and the open boxes of active plans, plus a notes section that is yours. Progress is not ticked by hand |

## How a plan moves

1. **Draft** in `tmp/`. Discuss it. Nothing is edited in the repo yet.
2. **Agree.** Move it here as `YYYY-MM-DD-<slug>.md` (the date is the day we agreed), add the `Status:` line, add one row to "Active plans" in `STATUS.md`.
3. **Work it.** Decisions are asked one at a time and recorded in the plan's decision table; steps are checkboxes ticked as they finish; code and doc changes follow the normal order (design rule, schema, validator or tooling, implementation, tests).
4. **Close.** Set `Status: done` (or `dropped`), add a short `Result` section, and take the row out of "Active plans". A finished plan stays here as history.
5. **Supersede.** Only a plan replaced by a newer one moves to `docs/_archive` (the repo-wide archive convention), after which it is ignored when reading.

## What a plan contains

- `Status:` line (`proposed`, `active`, `done`, `dropped`) and the date.
- The threads or goals, in the user's words where they matter.
- A vocabulary table if the plan introduces names.
- Decisions (ID, question, recommendation, answer) and phased steps as `- [ ]` checkboxes with an owner when it is not obvious.
- A `Result` section when closed.
- The raw brain-dump, word for word, at the end of a plan that came from one.

## Rules

- Big design decisions need the user's approval before any file is edited for them (for example the MVP element set).
- A plan states what is open; `STATUS.md` states what is decided. Do not copy one into the other.
- Keep lines under 500 characters (markdownlint), one home per fact.
