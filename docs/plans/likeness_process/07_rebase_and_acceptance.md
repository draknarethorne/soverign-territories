#### Recorded cause: retained cast seeds were reassessed by regrouping

The cast-seed phase and the final regrouping phase do not apply the same
placement contract. `_cast_seed_outcomes` initially retains core members
and protected photos. `group_lifecycle.regroup` then reassesses those rows:
its placement locks exclude automatic photo protection (records with
`protectionProvenance`) and exclude protected Sisters/Angels identities.
Core membership and `retainedCast` are not placement locks either.
Final routing sends tentative associations into a target's Review folder
and unresolved rows into Various/Review, then rewrites `retainedCast`,
`releasedCast` and `castSeedDecision` from final placement. The original
`castSeedReason` remains, explaining contradictory-looking receipts such
as a released row whose seed reason still says "protected photo".

Concrete receipt evidence: all 26 Draknava and all 25 Draknira originals
were marked core members, with 21 automatically protected photos in each;
all were released in final routing. Nyxene had 14 core members and 11
automatically protected photos among 15 originals; all were released.
These five depleted folders (also Drakness and Ravaelle) have no configured
identity anchors. The inspected protected-photo records have automatic
provenance, not explicit manual placement locks. This establishes how
initial retention was overridden; it does not establish whether the
underlying similarity decisions were correct. No scoring or face-grouping
change was made. A blanket cast lock would also contradict reassessment
of old membership and must not be presented as a proven matching fix.

The likely contract gap is not simply that global reassessment existed. In
`group_lifecycle.regroup`, original folders are lineage rather than a
default source-membership fallback; reconstructed references and the global

to that target's Review folder without supported-entry margin. This can
replace a weak source association with a tentative rival association even
when the source member has not been independently established as another
person. That conflicts with the Q&A's reference-withdrawal and
hypothesis-versus-identity safeguards unless the user selects a different
physical-routing rule.

The still-open point is how to physically route an uncertain photo when its
source evidence is weak and another parent is only tentative: preserve it
under its source as non-core, route it to the tentative parent's Review area

[scope-test proposal](../2026-11-12-member-refinement-scope-test.md) records

## Nov 11 FAST likeness-first rebase contract

The user clarifies the desired sequence: **FAST** does the minimum necessary
to intake, compare likeness, assign, move and rename photos without expensive
image creation; **LEAN** is the balance; **FULL** is complete final processing
after the likeness outcome is satisfactory. FAST is a processing/publication
profile, not another name for disposable recovery or smaller evidence storage.
This explicitly supersedes the older FAST-only-as-cheap-composition proposal
for this rebase use case; that proposal remains historical experiment context.

**Before the Nov 11 implementation increment:** the maintained rebase CLI
accepted only `--storage-mode full|lean`; there was
no supported FAST processing/profile switch. LEAN still assesses preparation
and emits the selected padded image, and clean-rebase install invokes
944x1104 derivative generation. Disposable recovery avoids the pre-intake
originals/backup steps, not the later derivative phase.
`--preserve-legacy-derivatives` handles existing-file collisions; it is not a skip-generation
option. Reusing verified saved preparation avoids repeated editing/intake,
but does not by itself provide the requested raw-image FAST lifecycle.

Verified against the actual launcher on Nov 11: `--help` exposes only
full/lean storage and full/disposable recovery; `--storage-mode fast
--dry-run` refuses with exit 2 before creating any run directory. This was
a parser-only probe, not an intake or reset. Source anchors:
[`clean_preparation.prepare`](../../../tools/art/likeness_library/clean_preparation.py),
[`image_preparation.render_photo`](../../../tools/art/image_preparation.py),
[`clean_rebase.install_plan`](../../../tools/art/likeness_library/clean_rebase.py)
and [`rebase_flow.steps`](../../../tools/art/rebase_flow.py).

| Boundary | Required FAST likeness-first behavior | LEAN / FULL relationship |
| --- | --- | --- |
| Input and identity | Inventory/hash/decode inputs, retain exact originals, stable IDs, deduplicate aliases without duplicate votes, preserve artist/general scope and explicit intent | Shared correctness and recovery requirements; not optional for speed |

| Likeness and routing | Run eligible discovery, references, comparisons, member/appearance state, assignment and final routing; preserve margins, protections, names, source lineage and exact movement ledger | FAST is not a weaker grouping/contamination policy or a matching-only report without file lifecycle |

## Acceptance sequence

1. Freeze full saved input, exact policy/recipe/code/manual scope, pixel/
   measurement compatibility, initial reference construction and resource
   budgets. Compare against reproducible applicable baseline behavior.
   Do not seed all generated old identities as irrevocable truths.
2. Reconstruct discovery, member-first reconciliation, appearance states,
   controlled reference growth/withdrawal, residual reconsideration,
   admission, continuity, readiness, downstream relationships and routing.
   Include all eligible decisions and full competitor context. Explicitly
   conserve quality-ineligible/missing-evidence rows without forced matches.
3. Emit complete old/new person/group/member/reference/selection/path ledger,
   including unchanged/held/unknown photos and their actual reassessment
   scope. Attribute direct human decisions separately from automatic gains.
   A lower identity or Review count is not the success criterion.
4. Check fixed-input reverse/repeat behavior, zero no-op churn and bounded
   convergence. Compare representative incremental arrivals and affected
   dependency expansion against equivalent full reassessment, with explicit
   mode/manual-intent differences and incomplete/escalation states.
5. Evaluate cast and non-cast recovery, mixed identities, distinct lookalikes,
   avoidable splits, reference purity, residuals and uncertainty against the
   fixed budgets. Include [03](03_secondary_evidence.md) before acceptance if
   face-only cannot meet the goal; do not hide that gap behind conservative
   holds or an unapproved permanent deferral.
6. Measure cold/warm/no-op extraction, decision, report and publication
   costs separately. Reuse cached pixels/features and shared run evidence.
   Do not rerun preparation/derivatives per scoring variant.
7. Present the actual candidate placements and exception ledger for bounded
   meaningful user review, with clear recommendation, group/member scores,
   reasons and action versus identity judgments. Request installation
   approval for this exact candidate, not an old report or hypothetical rule.
8. Install only the approved sandbox candidate through supported staging/
   publication/recovery. Verify actual Gallery/Overview/Review, group/path
   consumers, managed selection conflicts, hashes/counts and recovery under
   the applicable profile. Retain historical inputs and receipts.
9. Record explicit exceptions/owners and accepted versus deferred behavior.
   Only then decide whether full intake is appropriate. Production
   promotion remains separate; no implicit cutover from sandbox acceptance.
