## Code-path comparison

### Global member-first reformation

[`clean_rebase.create_plan`](../../tools/art/likeness_library/clean_rebase.py#L2147)
runs [`group_lifecycle.regroup`](../../tools/art/likeness_library/group_lifecycle.py#L148)
for the selected regroup mode. That operation:

1. Reconstructs cast reference views from `castSeedCore` and eligible anchors.
2. Pools other eligible, unlocked photos globally; original folders are
   lineage, not automatic membership.
3. Assesses every measured photo against the reconstructed target views.
4. Assigns supported, tentative or unresolved state and rewrites physical
   destinations accordingly.

In this path, `group_lifecycle.regroup` does not use a source-membership
low-score gate before reassignment. Automatic photo protection with
`protectionProvenance` is deliberately not treated as an explicit placement
lock. A tentative target needs the configured retention score and support,
but does not need the supported-entry margin; tentative assignment is routed
to Review. These choices may support a deliberate full rebase, but they do
not implement the Q&A's source-member retention and destination-admission
distinctions by themselves. In particular, a weak or withdrawn source
reference must not silently become evidence for another identity.

### Audit-aligned membership refinement

The separate [`refinement.refine_membership`](../../tools/art/likeness_library/refinement.py#L88)
path compares every eligible Gallery member and allows a move when a rival
outranks the own score and destination safeguards pass.
[`membership_decision`](../../tools/art/likeness_library/refinement.py#L19)
has no source-side minimum score or low-member-only eligibility gate.
Existing tests explicitly expect a move when the own score is `0.6` if the
rival qualifies. This path is also broader than the newly described
refinement theory, although it did not cause the 303 installed outflows.

### Related existing outlier logic

[`identity_maintenance.split_candidates`](../../tools/art/likeness_library/identity_maintenance.py#L161)
is closer to a low-member-first check: it evaluates alternatives only after
the member falls below `splitCandidateBelowSimilarity`, and then applies
independent target-routing gates. It is a separate maintenance path, not the
regroup implementation; cast automatic splitting is disabled in the current
category policy. Treat it as prior art for the test, not as evidence that the
full FAST rebase uses the same logic.
